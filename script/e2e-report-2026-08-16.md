1. **ACTION_SPOT_SEND (id 6)** — **VERIFIED WORKING.** Doc table confirms id 6 layout `(address, uint64, uint64)`; live: vault's spotSend to the USDC system address delivered exactly 10.0 EVM USDC to the vault's EVM address in ~13s. The single most load-bearing unknown is now closed.

3. **Outcome-leg fee → false-attest risk** — **NO RISK.** Split minted and merge burned outcome tokens in EXACT amounts (10.0 both ways). The merge fee lands on the **quote** side, which the keeper does not delta-match. Exact-delta matching on the outcome coin is safe.
4. **~7 bps round-trip loss** — **REPRODUCED AND ATTRIBUTED**: 7.0 bps merge fee + 0.058 bps-equivalent spotSend fee; split free. See accounting above.
5. **Core→EVM fee/rounding ratcheting `outboundExpectedEvm`** — **NON-ISSUE for tracking.** The spotSend fee is charged on top of the sent amount from the sender's remaining Core balance; the delivered EVM amount equals the sent amount exactly, so `_unlandedEvm` retired to 0 and `clearOutbound` was never needed. (But see mainnet note M3: the fee does need headroom.)

## New findings (not in the risk list)

- **F0 (blocker-class): USDC EVM→Core via CoreDepositWallet does not credit on current testnet.** Three controls: no Core account (lost), account but no USDC slot (lost), account + USDC slot (lost) — 22 USDC total sunk; correct `Transfer(deployer → 0x2000…0000)` events emitted by `0x0b80659a…` each time, no ledger entry, no credit after >30 min. The identical call worked in the 2026-08-14 spike. HYPE EVM→Core (`0x2222…2222` native send) credits in seconds throughout. Possible causes: testnet regression, or a new rule tied to Circle's CCTP-on-HyperCore rollout (Circle docs state testnet transfers require the recipient to exist on HyperCore **mainnet**; the spike wallet plausibly does, this deployer does not). Unresolved — `OutcomeVault.deposit()`'s EVM→Core leg is untestable on testnet today and every vault deposit's collateral would sit in the deposit wallet uncredited. **Must be re-verified (and the cause pinned) before any mainnet deployment.**
- **F1: Core accounts must pre-exist before receiving EVM→Core transfers**; credits to non-existent accounts are silently lost (not queued). The **vault contract's Core account is a deploy-time prerequisite**: activate it right after deploy via a Core-side spotSend of ≥ dust USDC (costs the sender a flat **1 USDC activation fee**; the recipient receives the full amount). EVM→Core self-transfer also activates but takes ~$1 out of the transferred token. This step belongs in the deploy runbook — it is currently in no script.
- **F2: big blocks are required for the vault deploy** (3.46M gas > 3M small-block limit). `evmUserModify {usingBigBlocks:true}` is an L1 action that itself requires the sender's Core account to exist — chicken-and-egg for a fresh deployer EOA (broken by the HYPE-send activation trick).
- **F3: pruning wipes the question binding**: 0x814 for a pruned outcome returns `question = 4294967295`, so `settle()`'s status-2 `QUESTION_MISMATCH` check is impossible at status 3 — consistent with the design (that path already trusts the keeper).
- **F4 (keeper nits, no code change made):** (a) at startup, `watchContractEvent`/settlement reads hit transient RPC "Request exceeds defined limit" errors for ~15s, then recovered; both live ops were still detected within 6–10s of their blocks. (b) The pruned-before-observed ALERT repeats every poll tick until recovered (unlike `holdAlerted`); it self-silences once `settled=true`. Arguably correct for a manual-action nag; flagged for an alert-dedup pass if log volume matters.

### 2 & 3. Keeper clock-skew margin + MAX_SAMPLE_AGE (Important #4a/#4b)

**What:** `newestSampleBefore` (`keeper/src/pure.ts`) gained two optional parameters, `marginMs = 0` and `maxAgeMs = Infinity` (both default to prior behavior, so existing call sites/tests are unaffected unless they opt in). The provenance cutoff is now `beforeMs - marginMs`, and a qualifying sample must additionally satisfy `readAt >= cutoff - maxAgeMs`.

`keeper/src/keeper.ts` defines and wires two constants at the call site (`sampleBefore`, which backs `resolveLiveBaseline`):
- `CLOCK_SKEW_MARGIN_MS = 2_000` — guards against the keeper's wall clock (`Date.now()`, used for `readAt`) running behind the chain's block timestamp (`beforeMs`), which would otherwise let a post-execution sample look "provably pre-op".
- `MAX_SAMPLE_AGE_MS = 60_000` — guards against a stalled sampler's arbitrarily old (but technically pre-op) sample serving as a "confident" baseline; a sample older than this no longer qualifies and the caller falls through to the existing unconfident/fallback path (`resolveLiveBaseline`'s catch branch, `confident: false`).

**Where:** `keeper/src/pure.ts` (`newestSampleBefore`), `keeper/src/keeper.ts` (`CLOCK_SKEW_MARGIN_MS`, `MAX_SAMPLE_AGE_MS`, `sampleBefore`).
**Tests:** two new cases added to `keeper/test/pure.test.ts` — one pinning that a sample which only qualifies without the margin is excluded once `CLOCK_SKEW_MARGIN_MS`-equivalent margin is applied (and that omitting the margin arg preserves old behavior), one pinning that a sample older than `maxAgeMs` is excluded even though it predates the cutoff.
